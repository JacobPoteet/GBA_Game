# Architecture

## The one important split

The game is divided into two halves that never mix:

```
              +-------------------------------+
   Butano --> |  scenes, sprites, input, text |   src/main.cpp
   depends    |  gp_title_scene, gp_game_scene|   src/gp_*_scene.cpp
              +---------------+---------------+
                              |  uses
              +---------------v---------------+
   no Butano  |  puzzle logic                 |   src/gp_board.cpp
   at all     |  gp::board, gp::cursor        |   src/gp_cursor.cpp
              +-------------------------------+   include/gp_tile_kind.h
```

The lower half includes nothing from Butano and allocates nothing. That is what makes `tests/`
possible: the host compiler builds those exact source files and exercises the rules in
milliseconds, with no emulator and no ARM toolchain. For a puzzle game this is the highest-value
structural decision in the repo — puzzle rules are where the bugs live, and they are pure
functions of the board state.

The rule to keep: **if a file includes a `bn_` header, it cannot be unit tested.** Push logic
down, keep rendering up.

## Scenes

`gp::scene` (include/gp_scene.h) is an abstract base with one method:

```cpp
[[nodiscard]] virtual bn::optional<scene_type> update() = 0;
```

Return nothing to stay on this screen, or a `scene_type` to switch. `src/main.cpp` owns the
current scene in a `bn::unique_ptr` and swaps it when `update()` asks. A scene owns its sprites
for its entire lifetime, so switching scenes destroys them automatically — no teardown code.

This is the same shape Butano's own `butano-fighter` uses, so its source is a useful reference.

## Board model

`gp::board` is a fixed 6x6 grid of `gp::tile_kind`. Two deliberate choices:

* **Out-of-bounds is not an error.** Reads return `tile_kind::empty`, writes are ignored. Callers
  (and future puzzle rules that scan neighbours) do not have to bounds check every access.
* **`fill()` is seeded and deterministic.** It carries a small xorshift32 rather than calling
  `bn::random`, so a test can assert exact board contents and a bug can be reproduced from a seed.

`gp::cursor` clamps at the edges instead of wrapping, and `move()` returns whether it actually
moved so the scene only redraws when something changed.

## Assets

Butano compiles art into the ROM at build time. Each asset in `graphics/` is a pair:

* `name.bmp` — **4bpp, 16-colour palette, uncompressed, BITMAPINFOHEADER**. Butano's parser
  (`third_party/butano/butano/tools/bmp.py`) rejects anything else, including the V4/V5 headers
  that most image editors write by default. Palette index 0 is transparent.
* `name.json` — `{"type": "sprite", "height": 16}`, where `height` is one frame's height. A
  16x64 sheet with `"height": 16` is four frames, selected by `graphics_index`.

The build then generates `bn_sprite_items_name.h`, giving you `bn::sprite_items::name`.

The current art is placeholder, generated by `tools/gen_placeholder_art.py` so it can be
regenerated or tweaked without an image editor. Frame order in `gp_tile.bmp` must stay in sync
with `gp::tile_kind` — `tile_kind_graphics_index()` is the mapping, and there is a test for the
round trip.

Text uses Butano's bundled `common_variable_8x16_sprite_font`, pulled in through
`third_party/butano/common`. Replace it with a project font when the game has a visual identity.

## Build systems

Two, on purpose:

| | Builds | Entry point |
| --- | --- | --- |
| `Makefile` | the GBA ROM, via Butano's `butano.mak` | `make` |
| `tests/CMakeLists.txt` | host unit tests only | `cmake -S tests -B build-host` |

The CMake project never builds the ROM and never sees Butano. Keeping them separate is what stops
the test build from needing devkitARM.

## Naming

Every file in `src/` and `include/` is prefixed `gp_` because Butano's makefile collapses all
source directories into one flat `VPATH`. Two files named `board.cpp` anywhere in the project
would silently collide. The prefix is not decoration.
